# Rust port: defects found and fixed by the audit

## feat-tempvoice, feat-events

- src/services/eventService.js createEvent (Rust event_service::create_event): when the first createEventRow answered LIMIT/HOST_LIMIT and the overdue sweep ended at least one event, the JS runs the second createEventRow inside the same try/catch, so a failure there is only warned about and the reply is the original 'Too Many Events'. Rust propagated that error with `?`, so /event create failed with a generic error instead. The sweep and retry now share one error path, warned about as in the JS. Test: tests/events_db/mod.rs create_event_retry_failure_after_the_overdue_sweep_answers_the_first_limit (25 open events, one overdue, title with a NUL byte so only the retry INSERT fails). It fails before the fix and passes after.
- src/commands/community/event.js create (Rust commands/event.rs create): the JS uses `guild.channels.cache.get(picked.id) ?? picked`, so a picked channel is always judged and posted in. Rust judged it from the serenity cache only and answered 'Cannot Post There / Channel not found' for a channel the cache lacked. A picked channel is now fetched with bot_core interaction_helpers::resolve_channel (cache, else REST, then cached) before check_channel_usable and member_can_post. Test: tests/events_db/mod.rs event_create_fetches_a_picked_channel_the_cache_lacks (FakeRest answers GET /channels/{id}). It fails before the fix and passes after.
- src/commands/admin/voice-hub.js runCreate/runEdit (Rust commands/voice_hub.rs): the JS reads `category`, `channel` and `hub` from the option's resolved channel. Its permission check (`missingBotPermissions(category ?? channel.parent ?? guild)`) therefore runs in the category even when the cache lacks it. Rust used the cache only, so an uncached category fell back to guild-level permissions: a hub could be created in a category where the bot lacks Manage Channels, and channel creation then failed silently on every join. After the defer, create/edit now fetch a picked channel the cache lacks (new picked_channel_fetched). Test: tests/db.rs voice_hub_create_judges_an_uncached_category_by_fetching_it (the category is only reachable over REST and denies Manage Channels; expects 'Missing Permissions … in **Late**' and no hub row). It fails before the fix and passes after.

## feat-levels, feat-achievements

- xpService.js reconcileVoiceMember, `guild.client.readyTimestamp ?? now` (Rust xp_service::ready_at): when neither the override nor App::ready_at_ms was set, Rust stored the first `now` and reused it on every later call. The JS evaluates it fresh each time. ready_at now returns `app.ready_at_ms().unwrap_or(now)` and stores nothing. Test: levels.rs ready_at_without_a_ready_time_is_the_current_now.
- xpService.js announceLevelUp (Rust xp_service::announce_level_up): Rust only looked in the cache and dropped the JS fallback `await guild.channels.fetch(id)`. A custom level-up channel or thread missing from the cache never got an announcement. It now uses check_channel_usable_fetch. Test: levels.rs announce_level_up_fetches_an_uncached_custom_channel (FakeRest serves GET /channels/{id}; the test checks for exactly one POST).
- leaderboard.js fetchMissingNames and xpService.js runBulkRoleSync, `guild.members.fetch({ user: ids })` (Rust xp_service::fetch_members): Rust made one REST GET per uncached member, 5 at a time. JS makes one gateway REQUEST_GUILD_MEMBERS per 100 ids. It now uses bot_core::guild_members::fetch_members_by_ids under the same timeout; errors are ignored and members that arrived are re-read from the cache, as the JS `.catch(() => null)` then `members.cache.get` does. Test: levels.rs fetch_members_asks_the_gateway_for_uncached_members (one gateway request, zero REST calls, departed member absent).
- xpService.js handleMessageXp, `isNoXpChannel(settings.noXpChannelIds, message.channel)` (Rust xp_service::handle_message_xp): when the hook payload had no channel and the cache missed, Rust skipped the no-XP channel check, so XP was granted in a no-XP channel. It now fetches the channel with resolve_channel, but only when the no-XP channel list is non-empty, so most guilds make no extra REST call. Covered by the existing message-XP tests; this branch has no dedicated test.
- birthdayService.js fetchMembers (Rust birthday_service::SerenityBirthdays::members): Rust made one REST get_member per uncached id. That is up to about 550 calls per tick, which risks rate limits and the 60 s job timeout. It now uses fetch_members_by_ids (gateway, 100 ids per request, 10 s), maps a timeout or unsent request to an error that propagates as the JS rejection does, and leaves unknown ids absent (left the guild). Test: birthdays.rs serenity_members_use_one_gateway_request_and_fail_on_a_timeout.
- bot.js shutdown `flushMessageCounts({ final: true })` (Rust feat_achievements::register / achievement_service::ensure_shutdown_flush): the shutdown flush was registered only on the first messageCreate dispatch. register() now installs it at boot through reg.on_boot (the on_message_create call stays as an idempotent fallback), and plugins.json hasInit stays false. Test: achievements.rs db_the_shutdown_flush_is_registered_at_boot_before_any_message; the existing buffer test also installs the registry now.
- community/achievements.js execute, `interaction.memberPermissions.has(ManageGuild)` (Rust commands/achievements.rs): discord.js `has` also counts Administrator (checkAdmin defaults to true); Rust checked only MANAGE_GUILD, so an Administrator-only member missed the 'Create one with /achievement-config ...' hint. Test: achievements.rs db_achievements_admin_hint_counts_administrator.
- community/achievements.js thumbnail `(member ?? user).displayAvatarURL({ extension: 'png', size: 128 })`: Rust did a string replace of size=256 to size=128. It now uses the bot-core member_display_avatar_url_with / user_display_avatar_url_with(ImageUrlOptions::new("png", Some(128))) helpers. Same output; workaround removed.
- xpService.js seedVoiceSessions and runVoiceSweep (Rust seed_voice_sessions_for, run_voice_sweep): one `now` was shared by every member, while the JS reconcileVoiceMember defaults `now = Date.now()` for each member. The clock is now read per member. Cosmetic: at most milliseconds of difference within a sweep.

## feat-logging, feat-general

- loggingService.js sendLog (guild.channels.fetch): when a log channel was not cached, the Rust SerenityLogApi::fetch_channel accepted a channel from any guild, so it could post log embeds into another server's channel. It also never cached the fetched channel, so every post made a new REST call. It now goes through bot_core::interaction_helpers::fetch_channel, which refuses another guild's channel (GuildChannelUnowned, a 30 s skip as in the JS) and caches what it fetched. Test: tests/logging.rs an_uncached_log_channel_is_fetched_for_this_guild_only_and_then_cached.
- discord.js InviteCreateAction / InviteDeleteAction emit nothing while the invite's channel is not cached, for example the invites of a deleted channel. Rust still ran all four invite hooks for those events. The two logging hooks posted 'Invite created/deleted' entries the JS never posts, and the two invites hooks edited the invite snapshot. All four hooks now return early when the channel is not cached (plugins/logging.rs invite_channel_cached). Test: tests/logging.rs invite_events_of_an_uncached_channel_are_ignored.
- logEvents.js buildMemberLeaveEmbed / diffMemberUpdate (adapters.rs log_member): roles were ranked by the raw API position, and role ids missing from the cache were included with position 0. discord.js uses member.roles.cache, which has only cached roles, and sorts by role.position (raw position, ties broken by id, the older role ranking higher). log_member now uses bot_core::permissions::role_position and drops uncached ids. Test: tests/logging.rs member_leave_lists_roles_by_discord_js_rank.
- inviteTracker.js trustedSince (client.readyTimestamp ?? Infinity): Rust trusted any snapshot taken after the tracker's first run in the process, even before the client was ready. Snapshots are now trusted only from app.ready_at_ms(), and nothing is trusted before ready, as in the JS. The time is read inside the guild mutex, as the JS does, and set_trusted_since remains as a test override. I checked that gateway.rs finish_startup sets the ready time before the startup guildReady hooks run, so warm snapshots stay trusted. Test: tests/invites.rs snapshots_are_trusted_only_from_the_ready_time.
- invites.js createLink: deleteDiscordInvite for a replaced link, and for a link that could not be saved, is fire-and-forget in the JS. Rust awaited it before replying. It now runs in a spawned task (spawn_delete). Test: the replace step in tests/invites.rs invites_link_creates_reuses_replaces_and_maps_failures now uses a delete that takes 1.5 s and checks that the reply arrives before the delete.
- invites.js createLink with channel:<option>: an option channel missing from the serenity cache was refused with 'Unsupported Channel'. discord.js uses the interaction's resolved channel. Rust now fetches and caches it with bot_core resolve_channel before the checks. Test: tests/invites.rs invites_link_fetches_an_uncached_option_channel.
- inviteTracker.js trackLeave: leftAt is now built from the clock in whole milliseconds, like a JS Date. Before, a sub-millisecond value was rounded by the timestamp(3) column. Covered by the existing leave and stats DB tests.

## feat-economy, feat-games

- daily.js / work.js `memberRoleIds` (Rust: feat-economy commands/mod.rs member_role_ids). discord.js `member.roles.cache` always includes the @everyone role (the guild id) and only roles that still exist. The Rust passed the raw payload roles instead. Effect: a coin boost on the @everyone role (which the dashboard can set) never applied, and a boost on a deleted role that the payload still listed did apply. Fixed with bot-core `member_role_ids(&guild, &member)`; when the guild is not cached, the fallback is the guild id plus the payload roles. Test: economy.rs `daily_boosts_see_the_everyone_role_and_only_existing_roles`. It failed before the fix.
- economy-admin.js itemCreate/itemEdit `guild.roles.cache.get(picked.id) ?? picked` (Rust: economy_admin.rs role_check). The Rust looked the role up in the cache only, so a role the interaction resolved but the cache did not hold yet was refused as 'Role not found.' It is now judged with `check_assignable_role` using the role the interaction resolved. Test: `item_create_judges_an_uncached_role_from_the_interaction`. It failed before the fix.
- Concurrent clicks, which are user-visible because bins/bot runs a multi-thread tokio runtime. The collector driver runs each click's handler on its own task, but several decisions checked a flag in one step and set it in a later one: (1) games.js rps `played` (load, then store), so one game could play two rounds; (2) games.js tictactoe challenge `settled`, so a double Accept started two game collectors (R090 broken); (3) games.js tictactoe moves re-checked the turn outside the lock, so two quick clicks by the same player placed two marks; (4) scrabble.js challenge `settled`, so a double Accept tried to start a second game and posted a stray '⚠️ A Scrabble game already started'. Each is now one test-and-set step (`AtomicBool::swap`, `mem::replace` under one lock, and the turn re-decided under the game lock; the losing click is answered as in the JS: deferUpdate, or "⏳ It's **X**'s turn!").
