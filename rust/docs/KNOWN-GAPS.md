# Rust port: known differences from the JavaScript bot

Written by the audit reviewers after comparing every crate with its JS source. Each entry names the JS file or function and how much it matters.

## feat-tempvoice, feat-events

- tempVoiceService.js snapshotOverwrites / grantableBits (user-visible, minor): serenity 0.12.5 drops permission bits it does not know (PinMessages, bit 51) when it reads overwrites and roles into its cache. Template overwrites copied from the hub or category lose a PinMessages allow/deny, and when the bot is not Administrator its own text-channel overwrite never carries PinMessages. Pinning the panel still works through the Manage Messages fallback. The bits Rust computes itself are sent intact (from_bits_retain).
- tempVoiceService.js queueHubJoin (edge case): before posting the control panel, Rust checks that the channel's row still exists, not guild.channels.cache.has(voice.id). Both run under the same ch: lock, and the row is purged in the same step as the delete.
- voice-roles.js onGuildReady (edge case): the place in the one-at-a-time startup queue is taken when the detached task first runs, not when the hook is called.
- voiceRoleService.js collectTargets (edge case): candidate members are taken in user-id order, not discord.js cache-insertion order. This only changes which members get checked when RECONCILE_MAX (1000) truncates the list.
- temp-voice.js guildReady / onVoiceStateUpdate hub join (cosmetic): settings come from get_settings_safe (memoised), not ctx.getSettings(). The result is the same.
- tempVoiceService.js countHumans (edge case, Rust is safer): the JS counts channel.members, which only holds members discord.js has cached. Rust counts every voice state in the channel, except members known to be bots. A member in voice whose member object is not cached counts as present in Rust. In the JS such a channel could look empty and be deleted, or be skipped by /voice clean.
- tempVoiceService.js reconcileGuild (edge case): members already waiting in a hub are taken from the guild's voice states (the state's member, else the cached member). The JS takes hubChannel.members, cached members only.
- commands/community/event.js create (edge case): a picked channel whose REST fetch fails (403/404/offline) still answers 'Cannot Post There: Channel not found'. The JS would carry on with the option's resolved partial channel.
- eventService.js readEditForm (edge case, forged forms only): a missing modal field reads as empty. In the JS, getTextInputValue throws and the reply is 'Could Not Save'.
- eventService.js resolveCategory (edge case): when several categories are named 'Events', Rust picks the lowest position (then lowest id). The JS takes the first one in cache order.
- eventService.js resolveChannel (edge case): a fetched channel that is not a guild channel counts as noAccess. The JS would return it as found. Event channels are always guild channels.
- eventService.js __setJobImpl (test seam only): not ported. Rust tests use the real scheduler store. __setRenderImpl is ported as event_service::set_render_impl.
- eventService.js requestRender (edge case): the trailing render is a tokio::spawn'd task (sleep, then render), not an unref'd setTimeout. A render that is due can still run during shutdown; it is idempotent.
- eventService.js plainDiscordText / buildCalendarPayload (cosmetic): guild names come from a snapshot of only the ids the description mentions (guild_name_maps), not live discord.js cache lookups. A command mention whose name contains '<' (`</a<b:id>`) is left as is, where the JS regex would turn it into /a<b.
- eventService.js memberNames (cosmetic): an uncached member is fetched with bot_core fetch_members_by_ids (gateway, else one REST call per id), and a user with http.get_user. The display name order is nick > global_name > username, as in discord.js.
- rolePersistService.js snapshotMember (edge case): discord.js's partial member at guildMemberRemove is member = None in Rust, which saves nothing. The JS also saves nothing when a partial has no known roles; a partial with cached roles could still be saved in the JS.
- Time zones (cosmetic): formatStartForEdit / formatStartFields / parseEventWhen use bot_util's own tz tables, not Intl. They match the JS goldens at the 2026 DST edges of the tested zones.
- eventService.js parseEventWhen and the edit form zone note (cosmetic): zoneLabel uses the `now` passed in, not new Date(). In production they are the same instant.
- eventService.js createDiscordEvent / updateDiscordEvent / voice-job notes (cosmetic): the '(...)' error text comes from bot_core::discord::error_message (Discord's message), clamped to 120. discord.js err.message carries the same text, except for non-HTTP errors.
- eventService.js deleteEventChannel / handleVoiceJob (edge case): serenity's delete_channel parses the channel object Discord returns. A 204 from a proxy would count as a failure, and the job would retry.
- voice-hub.js runDelete and the ignore-role / mod-role groups (cosmetic): the hub channel is read from cache (else the option's partial) for its display name only. No REST fetch is made before the defer.

## feat-levels, feat-achievements

- xpService.js handleVoiceStateXp (author's gap, still true; edge case): the levels hook runs second in HOOK_ORDER.voiceStateUpdate, so it does not take its per-member lock in gateway order. The JS cannot either, because it awaits getSettings before voiceMutex.run. Listener counts and voice facts are read inside the lock, as in the JS.
- levelconfig.js subNoxpRole/subNoxpChannel (author's gap, still true; edge case): `guild.available` is treated as 'the guild is in the serenity cache'. Old entries are pruned against cached roles, or cached channels plus threads. Practically the same while the guild is available.
- xpService.js syncLevelRoles (author's gap, still true; edge case, offline only): with no Discord connection each planned role change is reported in `failed` with the reason 'Discord is not connected'. The JS always has a client.
- levelconfig.js subRoleAdd (author's gap, still true; edge case): the reply goes through safe_reply. If it is not delivered, the bulk lock is released and no backfill runs, as in the JS, but Rust then returns Ok where the JS rethrows. Nothing is visible to users; only the error log differs.
- achievement-config.js collectRewards, birthday.js handleRole, levelconfig.js subRoleAdd (author's gap, still true; edge case): role assignability is checked against the cached guild. If the guild is not cached, Rust answers 'Role not found.' where the JS checked the option's role object. In production the guild is always cached.
- achievementService.js message buffer timers (author's gap, behaviour identical): each waiting member's setTimeout is a spawned tokio sleep task, aborted when that member is flushed.
- birthdayService.js tickGuild (author's gap, behaviour identical): the 40 s deadline uses std::time::Instant (real time), like Date.now() in the JS. The tick's `now` parameter only sets the local date and hour.
- achievementService.js loadMemberView (author's gap, API shape only): it takes a boolean `boosting` (premiumSinceTimestamp is set) instead of the member object.
- xpService.js countOtherListeners on `channel.members` (new; edge case): Rust counts voice states whose member is not in the cache as non-bot listeners. discord.js channel.members contains only cached members. With the Guilds and GuildVoiceStates intents, voice-state members are nearly always cached.
- xpService.js reconcileVoiceMember, `state.channel` (new; edge case): Rust uses state.channel_id even when that channel is not cached. JS then sees state.channel as null and treats the member as 'no-channel' (not eligible). Rust is slightly more lenient.
- levelconfig.js subAnnounce, achievement-config.js announceMode/announceChannel, birthday.js handleChannel (new; edge case): the channel picked in the option is checked against the cache only. discord.js would check the interaction's resolved channel object. With the Guilds intent every channel is cached, so this matters only for an uncached thread or channel.
- xpService.js buildLevelUpPayload, `Number.isInteger(embedColor) ? embedColor : COLORS.SUCCESS` (new; cosmetic): a negative stored embedColor falls back to SUCCESS in Rust, while the JS passes the negative number on. Only reachable with corrupt data.
- xpService.js handleRoleDelete (new; edge case): Rust reads the settings before deleting the LevelRole rows; JS deletes first. The result is the same.
- birthdayService.js applyTierChange 'remove' (achievementService.js; new; cosmetic): completedAt is set with Utc::now() rather than the app clock, and an update of a missing Achievement id is silently a no-op where Prisma's update throws P2025. Unreachable from the commands, which resolve the row under the config lock first.
- Documentation (not code): the 'Known gaps' sections of rust/docs/api/feat-levels.md and rust/docs/api/feat-achievements.md are now out of date for the six gaps closed above. Those files are outside this reviewer's write scope.

## feat-logging, feat-general

- invite_tracker.rs observe (inviteTracker.js observe with withTimeout): after the 5 s timeout, the invites or vanity REST call is cancelled. In the JS it keeps running in the background and its result is thrown away. Nothing visible changes. Cosmetic.
- adapters.rs log_member / log_events.rs diff_member_update (logEvents.js diffMemberUpdate): in the 'Member roles changed' entry, added and removed roles are listed in the member's API role order, not in discord.js's guild role-cache order. serenity keeps guild roles in an unordered map. The same roles are shown, possibly in a different order. Cosmetic.
- plugins/logging.rs on_channel_update / on_role_update / on_guild_update (logging.js): when the gateway update has no cached old object, nothing is logged. discord.js does not emit these events without the old object either. on_thread_update diffs against an empty old thread, which gives no lines and so no entry. Edge case.
- adapters.rs log_guild / log_partial_guild (logEvents.js diffGuild 'AFK Timeout'): serenity stores afk_timeout inside afk_metadata, which is absent when no AFK channel is set. On a server without an AFK channel, a change of only the AFK timeout is not logged; the JS logs it. Edge case.
- plugins/logging.rs on_member_leave (logging.js onMemberLeave): when the member was not cached, the leave is logged from a partial view built from the user: no roles and 'Time in Server: Unknown'. This matches discord.js's partial GuildMember. Edge case.
- invite_tracker.rs invite_to_state (inviteToState): serenity's RichInvite has no expires_at, so the expiry is computed as created_at + max_age. That is discord.js's own fallback. It matters only for the 'vanished single-use invite' attribution rule. Edge case.
- invite_tracker.rs SerenityInviteApi::fetch_vanity: serenity's vanity call drops 'uses', so a raw GET /guilds/{id}/vanity-url is sent instead. Same data. No visible difference.
- plugins/logging.rs is_bot_managed_channel (logging.js isBotManagedChannel): one SELECT EXISTS(StatChannel) OR EXISTS(TempVoiceChannel) replaces two Prisma findUnique calls. Same result, same 10-minute memo. No visible difference.
- adapters.rs log_message (logEvents.js extractMentions over message.mentions.roles): role mentions are named from the guild cache, and uncached roles are skipped, as discord.js's resolved collection does. Edge case.
- logging_service.rs flush: the JS returns the in-flight flush promise to a second caller. Rust waits on a per-channel lock and then drains again, which finds nothing new. After a channel is marked dead, an old 1 s timer task can still fire one early flush for a newly created queue. Entries may be posted slightly sooner, never duplicated. Cosmetic.
- commands/logging.rs sub_ignore_add: the category name and type come from the resolved option when present, otherwise from the cached channel. Same output in practice. Cosmetic.
- feat-general commands/info.rs RoleView::of (info.js buildRoleEmbed role.tags): serenity always has a tags struct. A role is treated as having tags when any tag field is set. A non-managed role sent with an empty tags: {} gets no 'Managed by' field, where the JS shows 'Unknown'. Edge case, cosmetic.
- feat-general commands/info.rs UserView::of: badges are read from serenity's u32 public_flags. Flags above bit 31 are invisible, but none of them is a badge, so the output is the same. No visible difference.
- feat-general commands/info.rs fetch_member (info.js guild.members.fetch): a member fetched over REST (not cached) is not added to the serenity cache, whereas discord.js caches it. The only effect is a repeat REST call on the next /info user for that member. Cosmetic.
- feat-general commands/owner.rs: BOT_OWNER_ID is read from AppConfig, which is loaded at boot, not from process.env on each call. The JS process.env does not change at runtime either. No visible difference.
- feat-general commands/help.rs custom_command_group: the 3 s timeout cancels the CustomTag query, while the JS withTimeout lets it run on. The debug log text on a timeout may differ slightly. Cosmetic.
- feat-general bot_join_service.rs find_inviter_with: the audit-log and integration reads are raw REST GETs parsed as JSON, mirroring what discord.js reads. The application id comes from serenity's http.application_id(), falling back to the bot user id as in the JS. No visible difference.
- feat-general replies through interaction_helpers Payload::no_mentions send allowed_mentions {parse:[],users:[],roles:[]} where the JS sends {parse:[]}. Discord treats the two the same. No visible difference.
- feat-general commands/help.rs build_groups: categories come from each crate's CommandDef.category. The /help groups match the JS only while every crate declares its JS folder name. All 79 commands do so today. User-visible if a future command declares a wrong category.

## feat-tickets, feat-reactionroles

- feat-tickets, ticketService.js publishPanel: the published message is edited directly instead of being fetched first. A 10008 on the edit leads to a new post, the same result as the JS fetch failing. Edge case.
- feat-tickets, ticketService.js publishPanel / refreshPanelMessage: a database error is described as 'Discord error unknown'. The JS prints describeDiscordError of the Prisma error, e.g. 'Discord error P2025'. Cosmetic.
- feat-tickets, ticketService.js handleTemplateSubmit: if saving the template fails, or the panel lookup throws, the user gets a ticket-panel error embed (UNKNOWN / SLOW). In the JS the error goes to the component router's generic error reply. Cosmetic, rare.
- feat-tickets, ticketService.js handleLifecycleButton: a database error in getTicketById answers 'Ticket not found' (TICKET_NOT_FOUND). In the JS it rejects to the router's generic error. Cosmetic, rare.
- feat-tickets, ticketService.js renderTranscriptHtml: Intl.DateTimeFormat('en-GB') is reimplemented (format_en_gb). It matches the JS byte for byte in the tested time zones; years before 1 rely on bot_util's era years. Edge case.
- feat-tickets, ticketService.js parseOptionEmoji: grapheme splitting uses unicode-segmentation, not Intl.Segmenter. The emoji sweep matches the JS today; a future Unicode or ICU upgrade could drift. Edge case.
- feat-tickets, ticketService.js transitionFor with an unknown action: actions are an enum, so an unknown button action is rejected while parsing and answered 'This button is no longer active.', as the JS answers. No visible difference.
- feat-tickets, views (categoryLine, panelListLine, buildPanelDetailsEmbed, optionLine): a column holding an empty string ('' instead of NULL, which only hand-edited data can contain) is treated as set where the JS treats it as unset (e.g. 'deleted' instead of 'not set'). Edge case.
- feat-tickets, channel lookups: when the REST fetch itself fails (Discord down, a channel of another guild), the commands still answer 'not a ticket' / 'Channel not found', as the JS does when interaction.channel or the option object is missing. No change needed; noted for completeness.
- feat-reactionroles, reactionRoleService.js handleRoleButton/handleRoleSelect: the JS answers 'Something went wrong' (OOPS) when interaction.guild is not cached. Rust needs only the guild id and the member, and carries on. Edge case (guild not yet cached).
- feat-reactionroles, reactionRoleService.js hasManageMessages(guild, channelId, fallbackChannel): the fallback (the reacted message's channel object) is still not used. A panel channel that is neither cached nor fetched counts as 'no Manage Messages': the bot does not take back an over-the-limit reaction or the swapped-out Unique reaction, and logs the throttled warning instead. Edge case (uncached channel).
- feat-reactionroles, reactionRoleService.js fetchPanelMessage (channel.messages.fetch): SerenityRr::fetch_message always reads over REST first, because serenity's message cache does not track reactions. This costs one extra REST call per reaction-panel operation, with no visible difference.
- feat-reactionroles, roleTemplateSetup.js setupRoleTemplate/upgradePanel: the role is created with an explicit REST body {name, permissions:'0', mentionable:false, hoist:false, colors:{primary_color}}. discord.js builds its own body, so the JSON may differ slightly (e.g. secondary/tertiary colours left out rather than null). The created role is the same. Cosmetic.
- feat-reactionroles, admin/reactionrole.js new_role: discord.js caches a created role at once. Rust still takes a role missing from the cache from the interaction's resolved data and adds it to a cloned guild for checkAssignableRole (picked_role/assignable). Same verdict; no visible difference.
- feat-reactionroles, admin/reactionrole.js create/attach/repost: an uncached picked channel is fetched over REST and judged. The JS create uses only guild.channels.cache (and repost falls back to the panel's own channel when the picked one is uncached). Rust is more lenient: it accepts a channel the JS would refuse as 'Invalid Channel' or would ignore. Edge case.
- feat-reactionroles, admin/reactionrole.js autocomplete 'item': with more than 100 roles whose name matches the query, Rust picks the 100 role ids in hash order rather than discord.js's cache order, so a different subset can be searched. Edge case.
- feat-reactionroles, onMessageDelete: when the guild is not in the guild directory as available (not just 'unavailable'), Rust skips flagging the panel. The JS only skips when guild.available === false. Edge case at startup.
- feat-reactionroles, UNICODE_EMOJI_RE / graphemes: property tables copied from V8 (Unicode 17, ICU 78.3) plus unicode-segmentation. The 8080-entry sweep matches V8 exactly, but a future Node/ICU upgrade needs the tables regenerated (fixtures/gen/feat-reactionroles-emoji-tables.mjs). Edge case.

## feat-tags, feat-embeds, feat-automations

- feat-automations runtime.rs run_pin (JS ACTION_RUNNERS.PIN), user-visible: the 'Pin Messages' pre-check is skipped because serenity drops permission bit 1<<51. When the bot lacks the permission, Discord's 50013 is recorded as "I'm missing a permission for this" instead of "I need Pin Messages in <#…>". The run also counts as attempted, so 'uses' goes up where the JS would not.
- feat-automations runtime.rs enqueue_run (JS enqueueRun with withTimeout 30 s), edge case: a run that takes longer than 30 s is cancelled mid-way in Rust. In the JS the queue moves on but the run keeps going in the background, so a very slow run (for example one rate-limited by Discord) can stop partway in Rust.
- feat-automations options.rs import_role_hierarchy_problem (JS importRoleHierarchyProblem), edge case: the 'Your roles could not be checked.' branch cannot happen, and roles at the same position are ordered by id (bot-core's computed order) rather than by the raw position.
- feat-automations runtime.rs usable_target / run_reply (JS usableTarget, REPLY), edge case: when the event's own channel is not in the cache (the hooks read it from the cache), the action records a problem and is skipped. The JS always had message.channel.
- feat-automations plugin.rs on_message_delete (JS onMessageDelete), edge case: the member comes from the guild member cache only. The JS tried message.member first.
- feat-automations runtime.rs allowed_mentions_for and feat-embeds allowedMentions, cosmetic: serenity always sends users: [] and roles: [] next to parse. Discord treats this the same as the JS { parse: [...] }.
- feat-automations pure.rs discord_error_text and feat-embeds embed.js E_DISCORD / the welcome-channel PARTIAL text, cosmetic: Discord error messages come from bot_core::discord::error_message (serenity), not discord.js DiscordAPIError.message, so the 50035 and default texts can be worded slightly differently.
- feat-automations runtime.rs record_problem, cosmetic: the Redis write of the last-problem key is awaited instead of fire-and-forget. Only the ordering differs.
- feat-embeds embed_service.rs parse_import_payload (JS parseImportPayload), edge case: serde_json rejects some inputs JSON.parse accepts, such as lone surrogate escapes and 1e400. With duplicate keys the last value wins but keeps the first key's position.
- feat-embeds embed_service.rs update_published_embed (JS updatePublishedEmbed), edge case: a stored channelId or messageId that is not a valid snowflake is treated as CHANNEL_GONE, and the embed becomes a draft again. The JS would have got a REST error.
- feat-embeds embed_service.rs set_up_welcome_channel with create:false, edge case: the channel the command was run in is now also fetched over REST when it is not cached. discord.js read it from the cache, so Rust is slightly more lenient.
- feat-tags tag.js actionAdd (role actions), edge case: when the guild is not in the serenity cache, the give/remove/toggle role check (check_assignable_role_cached) answers 'Role not found.' (fail closed). In production the guild is cached.
- feat-tags tag.js guarded (role-hierarchy guard on edit/toggle/cooldown/permissions/action/response), edge case: when the guild is not cached the guard is skipped. The JS would answer 'Your roles could not be checked.'
- feat-tags tag_io.rs DiscordIo (JS runTag reading the live discord.js cache), edge case: the cached guild is snapshotted once per invocation, so a role or channel change during one run is not seen.
- feat-tags tag_service.rs run_tag role steps (JS member.roles.cache.has), edge case: Rust remembers roles it added or removed earlier in the same run. Two role actions on the same role in one command (for example toggle, toggle) therefore see the updated state. The JS saw the discord.js cache, which only updates when the gateway event arrives.
- feat-tags tag_service.rs handle_prefix_invocation / handle_triggers (JS `if (!message || !guild || !guildId) return`), edge case: Rust does not require the guild to be in the cache before running. It degrades (bare channel scope, roles without the deleted-role filter) instead of staying silent.
- feat-tags tagService.js getEffectiveActions, log only: the 'unknown actions format' warning (once per tag per hour) is logged from run_tag, /tag info and /tag action list, but not from buildUsage, /tag list, the autocomplete or the role-hierarchy guard.

## feat-welcome, feat-captcha

- Scope of this review: I compared welcomeService.js, applicationService.js (all of it), commands/admin/welcome.js, captchaService.js (the flow, hooks, timeout job, verify-existing, panel publish and refresh) and stickyService.js (scheduler and memo) line by line. I checked commands/admin/captcha.js lines 1-270 and the lock confirm text, and commands/community/application.js usableChannel, role and question limits. For the rest of commands/admin/captcha.js (270-572), commands/admin/sticky.js, plugins/sticky.js and stickyService.js 200-483, I only searched for REST lookups, cache lookups, string lengths, slices and number parsing. Those parts are covered by the author's JS-generated golden sweeps but were not walked line by line.
- welcomeService.js buildWelcomePayload (cosmetic, practically unreachable): there is no catch-all fallback to the default text, because the Rust rendering cannot throw. The 50035 default-text retry in sendWithFallback and sendWelcomeDm is ported.
- applicationService.js decide (no user-visible effect): the applicant is always fetched over REST through DiscordIo::fetch_member, where the JS guild.members.fetch reads the cache first. The result is the same, with one extra REST call.
- commands/community/application.js runPanel (kept on purpose; it matches the JS): when the channel option is refused, the refusal is answered and the panel is still posted in the current channel, as the JS does.
- Serialization differences (cosmetic; Discord renders them the same): allowed_mentions carries roles: [], buttons carry disabled: false and no emoji.animated: false, review and status embed fields carry inline: false where the JS left inline out, and thumbnails carry a null proxy_url, height and width.
- welcomeService.js toDbData (no behaviour difference): it is kept as a pass-through. bot-db already writes null on a Json? column as SQL NULL (Prisma.DbNull).
- captchaService.js renderCaptchaImage (cosmetic): the image is drawn with tiny-skia and the embedded Nunito font, not Skia, so it is not pixel-identical. The size, colours, noise, rotation and PNG format follow the JS.
- captchaService.js isImageCaptchaAvailable / MSG.FONT_MISSING (unreachable): the font is compiled into the binary, so image mode is always available and the font-missing fallback text never appears.
- captchaService.js publishPanel / refreshPanel (edge case): the stored panel is edited with PATCH directly, without messages.fetch first. A 10008 still re-posts the panel and permission codes still map to CaptchaConfigError.
- captchaService.js diagnoseCaptcha (edge case): the panel check is always a REST GET with a 3 s timeout. discord.js read its message cache first.
- Still cache-only, as in the JS and therefore not a difference: captcha's stored channel and role (guild.channels.cache.get(settings.captchaChannelId)), applicationService reviewChannelIssue and refreshPanel, welcome diagnostics and cardChannelWarning, and the sticky list orphans. One real difference remains: when the bot reconnects and a guild's channels are not cached yet, these say 'deleted' where discord.js would have the channel only if it was cached. The same holds in the JS.
- captchaService.js discordErrorText (cosmetic): the default branch uses serenity's error text, so its wording can differ from DiscordAPIError.message.
- captchaService.js startVerifyExisting (no user-visible effect): guild.available comes from the guild directory, and the batch runs in a tokio::spawn task instead of an un-awaited promise.
- captchaService.js applyLock / removeLock and the role creation in setup (edge case): if Discord applies a role edit but serenity cannot parse the returned Role, the change is reported as a failure.
- stickyService.js createScheduler (no user-visible effect): the debounce uses tokio timers. The JS `now` parameter is replaced by tokio::time::Instant, and the `_scheduler` export is has_pending(app, channel).
- plugins/sticky.js mayBeSticky (edge case): a deleted message that was not cached counts as partial, matching discord.js.
- API changes for other crates (none call these today): welcome_service::check_config_channel is now async. New public functions are welcome_service::add_autorole_resolved, welcome_service::adopt_resolved_role, captcha_service::check_verified_role_resolved and captcha_service::adopt_resolved_role. rust/docs/api/feat-welcome.md and feat-captcha.md are outside my crates and still describe the old known gaps; they need updating.

## feat-moderation, feat-automod

- feat-moderation create_infraction (JS createInfraction DM title): when the guild is not in the cache, the DM to the member says 'You were warned in ' with an empty server name. Cosmetic and rare, because the bot's guilds are cached.
- feat-moderation perform / unban_locked / unmute_locked (JS executeModAction etc.): when the guild is not in the serenity cache, Rust answers 'I couldn't load my own server member' instead of trying. The JS always had the guild object. This is an edge case: it only happens during startup or an outage.
- feat-moderation deliver_mod_reply ANONYMOUS (JS deliverModReply): if the public channel post fails because the interaction is gone, the JS rethrew and logged nothing. Rust shows 'I couldn't post the public notice here' and then logs only the follow-up error. Cosmetic.
- feat-moderation commands/purge.rs execute: there is no Rust equivalent of the JS outer catch reply 'Something went wrong while purging'. The Rust collect, delete and report steps never fail; a panic is caught by the router and the per-channel lock is released by a Drop guard. Edge case.
- feat-moderation commands/purge.rs deletable(): it is now exact for message types. It does not recheck channel viewability or Manage Messages per message, because /purge has already required both. Edge case: permissions changing mid-purge are caught by the 50013 stop instead.
- feat-moderation: job cancels and schedules that the JS ran 4 at a time with mapLimit (supersede, unmute close_rows, ban sync, reconcileExpiries) run one by one. The results are the same; only latency differs.
- feat-moderation is_snowflake / execute_unban: a 20-digit id above u64::MAX passes the JS-identical regex but is parsed as user 1. Discord ids never reach that. Theoretical.
- feat-moderation find_audit_entry: the 1.5 s wait is configurable per app (AuditDelay); production is 1500 ms as in the JS. Test-only difference.
- feat-moderation minor JS-number edge cases: perm_backoff truncates a fractional permRetries (the JS would keep 1.5); max_snowflake ignores '' (JS BigInt('') is 0); build_audit_reason uses 'unknown' for an empty moderator id (the JS would use ''). The code never produces these inputs.
- feat-moderation run_unban_job: a mod.unban payload whose infractionId is not an integer is treated as 'already handled' (Done). The JS's Prisma call would have thrown and retried until maxAttempts. Edge case: only for hand-edited jobs.
- feat-automod guild_invites (JS checkInvites guild.invites.cache): the server's own invite codes come from feat-logging's invite-tracker snapshot. An own invite the tracker has not recorded counts as a foreign invite and is acted on. User-visible in rare cases; the vanity code is handled.
- feat-automod incidents_of / set_incident_actions (JS guild.incidentsData): Discord's answer is used for at most 60 s, and only while the cache still shows the old value, until GUILD_UPDATE arrives. Edge case.
- feat-automod AutomodInput::scope (JS scopeChannelIds): if neither the event nor the cache has the channel, a thread's parent and category exemptions are missed. Edge case.
- feat-automod is_staff (JS isStaff/isImmune): feat_moderation::is_immune_member returns false when the guild is not cached, so the owner and immune-role part of the staff bypass is lost then. The MODERATOR-level and Manage Messages checks still run. Edge case.

- collate.rs name_compare (server.js and discordApi.js nameCollator, Intl.Collator en/base/numeric) approximates ICU. - dashboard.js process handlers: the Rust binary has no unhandledRejection or uncaughtException equivalent. A panic in a background task (not a request) goes to stderr through the default panic hook instead of logger.error, and does not exit the process with 1. Edge case.
- static_files.rs PublicDir::Embedded (server.js PUBLIC_DIR): by default the front end and CHANGELOG.md are embedded at build time, so editing src/dashboard/public or CHANGELOG.md needs a rebuild. - discord_api.rs load_guild_resources and server.rs guild_list (Promise.all): futures::try_join returns the first error it polls, which may not be the first to reject in time. When two Discord calls fail differently, the answer or log line can name the other error. Edge case.

- auth.rs OAuthClient::send (auth.js postForm, redirect: 'error'): a 3xx answer becomes 'fetch failed' with no status, as real fetch throws. Timeouts give 'The operation was aborted due to timeout'. Other undici-specific error texts are not reproduced, so the 'Dashboard login failed: ...' log text can differ. Cosmetic.

- /poll create with a picked channel missing from the cache, commands/community/poll.js create: Rust asks Discord for the channel within half the answer window. If that times out or fails, it answers 'Channel Not Found'. The permission checks then use the channel's real overwrites, which is stricter and more correct than the JS, which ran them on the interaction's resolved channel without overwrites. Impact: edge case, user-visible only for archived or uncached threads.
- /giveaway start and /giveaway restart with a picked channel that is neither cached nor fetchable, giveaway.js optionChannel: Rust answers 'Unsupported Channel'. The JS would use the raw resolved object. Impact: rare edge case.
- Message JSON in giveaways and polls, giveawayService.js and pollService.js embeds: serenity adds type 'rich' to every embed and writes whole-second timestamps without milliseconds. Discord treats both the same. Impact: cosmetic, invisible.
- giveawayService.js endGiveaway and pollService.js guildFor: a guild missing from this process's guild directory counts as unavailable, the same as guild.available === false. Impact: edge case.
- giveawayService.js scheduleCountRefresh and pollService.js requestRender: the timers are one-shot tokio tasks that resetCountRefresh and cancelRender invalidate by generation or token instead of clearTimeout. A cancelled task wakes up and does nothing. Impact: none visible.
- pollService.js postPoll test seams (deps.createPoll and the rest) are replaced by the app-wide DiscordOps seam. The logPrefix is kept through post_poll_with. Impact: none for the bot owner.

## feat-feeds, feat-translation

- ACTION FOR THE OWNER, user-visible (feat-feeds src/js_date.rs date_parse; feedParsers.js dateOrNull, Date.parse). A feed date written without a time zone is read in the zone named by the TZ environment variable, or UTC when TZ is unset. The JS bot reads it in the server's operating-system zone. If the host is not on UTC and TZ is unset, those feed dates are read up to ±14 h differently. That changes which items count as too old and the order items are posted in. Fix: set TZ to the same zone for both bots, or run both in UTC. Separately, during a daylight-saving gap Rust uses the offset from 3 hours earlier. This is an edge case.
- Edge case (feat-feeds src/xml.rs skip_doctype; fast-xml-parser DocTypeReader). <!ELEMENT, <!ATTLIST and <!NOTATION are skipped to the next '>', and an <!ENTITY inside one of them is an error. In practice there is no difference, because parseXmlFeed refuses any <!ENTITY and only a fifth or later DOCTYPE ever reaches the parser.
- Edge case (feat-feeds feed_parsers.rs looks_like_html / entry_summary, feed_service.rs; the JS slice(0, 1000) and slice(0, 5000)). When the JS cuts a string in the middle of an emoji pair it can leave half of the pair. Rust drops the half instead. This is at most one invisible character at the end of a cut summary.
- Edge case (feat-feeds feed_service.rs revive_cached; feedService.js reviveCached). A cached item field with the wrong type (for example a title that is a number) becomes '', None or false. The JS spreads whatever value is there. Only a cache writer other than these two bots can cause this.
- Cosmetic (feat-feeds commands/feed.rs and commands/reminder.rs). The reply after a defer goes through safe_reply: editReply, falling back to followUp when the original reply was deleted. The JS calls editReply directly. no_mentions() is sent as {parse:[],users:[],roles:[]} rather than {parse:[]}. Discord treats the two the same.
- Edge case, ordering only (feat-feeds commands/reminder.rs create_cmd, the form path; reminder.js createCmd). The row is created and then scheduled in a spawned task, and the form waits for the row over a oneshot channel. In the JS, scheduling is chained on the create promise. The order, the 'Still Saving' timeout and the replies are the same.
- Edge case (feat-feeds commands/feed.rs and commands/reminder.rs, the ping_role option). Whether the role is mentionable is read from the guild cache first, then from the role the interaction resolved. The JS reads the resolved role first. This differs only if the role changed between the two reads.
- Edge case (feat-feeds commands/feed.rs, reminder.rs and plugins/reminders.rs; checkPingRole and the reminder-modal permission check). Member role lists come from the raw interaction member (member.roles) rather than discord.js's member.roles.cache, which adds @everyone and drops roles that no longer exist. This does not change the result, because Discord removes deleted roles from members and @everyone is checked separately.
- Edge case (feat-translation user_timezone_service::member_role_ids and plugins/autotime.rs TimeMessage::of; userTimezoneService.js memberRoleIds). Same raw member.roles list. A timezone role linked to @everyone would not be seen, but neither /settings nor the dashboard allows that link (the dashboard role field refuses @everyone). A deleted role still in a stale member list gets position -1. In practice this cannot happen.
- Edge case (feat-translation translation_service translate_text, the cache hit; translationService.js translateText). A cached {t,d} value whose d is not a string reads as null. The JS would pass the raw value through. Only a foreign cache writer can cause this.
- Cosmetic (feat-translation build_auto_reply_payload and the autotime reply). serenity sends allowed_mentions as {parse:[],users:[],roles:[],replied_user:false}; the JS sends {parse:[],repliedUser:false}. Discord treats them the same.
- Log text only (feat-translation translation_service do_fetch; translationService.js doFetch). Network error messages come from reqwest, not undici ('fetch failed'). They appear only in logs and in the LibreTranslate failover reason.
- Not reachable (feat-translation translation_service language_name; translationService.js languageName via Intl.DisplayNames). A hyphenated code outside LANGUAGES returns the raw code, where Intl.DisplayNames would give a name. No caller can pass one, because normalizeLangCode only yields base codes or zh-tw.
- No visible effect (feat-translation get_languages; translationService.js langCache). The JS keeps a memo of the language list; Rust rebuilds it each time with the same result.
- Tests only (feat-translation commands/autotranslate.rs and commands/autotime.rs, ignore add). When the interaction carries no resolved channel data, the channel type and name come from the guild cache. Discord always sends resolved data.
- What the tests cover: parsers, URLs, dates, the XML tree and feed normalisation, markdown escaping and translation text preparation were fuzzed against Node with 0 mismatches. Every Discord REST call was tested only against bot-core's FakeRest and the crate's own seams, never against live Discord. The Google and LibreTranslate HTTP traffic was tested only with canned responses through the HttpTransport seam.

## bot-core, bot-db, bot-util, bot-config, bot-cards, rust/bins/bot. All six were built and tested at the start: the previous reviewer left nothing broken, and its fixes. Prisma's behaviour for empty updates was measured with Node probes against the mock database.

- index.js ShardingManager (worker mode, totalShards 'auto', respawn false): every shard runs in one process on serenity's shard manager. 'Spawning Shard N...' is logged after login has started. There is no 'Shard N reconnecting...' line. Any client exit is reported as 'Shard 0 died/disconnected'. User-visible in logs only.
- index.js boot: a ShardingReadyTimeout with fewer spawned shards than expected exits the JS; Rust always keeps running and lets /readyz report it. Edge case.
- utils/logger.js shardPrefix: lines have no '[Shard N] ' prefix, because set_shard_id is never called (SHARDS/SHARD_ID env still work). Cosmetic.
- index.js process.on('uncaughtException' → exit 1) and 'unhandledRejection': not ported. Task panics are caught and logged; a main-thread panic exits 101. Edge case.
- index.js signals: on Windows only Ctrl+C (handled as SIGINT); SIGTERM and SIGINT on Unix. Edge case.
- index.js STATE_DIR and commandLoader.js HASH_FILE resolve against the working directory, not the repository root: run the binary from the repo root. User-visible if launched elsewhere.
- Docker CMD `prisma migrate deploy`: the Rust binary applies pending Prisma migrations on every start when DATABASE_URL is set; `npm start` outside Docker did not. A modified migration is a warning. User-visible (intended).
- dotenv/config: .env.vault and DOTENV_KEY are not supported. DOTENV_CONFIG_ENCODING is ignored (UTF-8 is used). DOTENV_CONFIG_DEBUG/QUIET log nothing. Keys containing '=' or NUL are skipped. Edge case.
- index.js HEALTH_PORT: an invalid value goes to the error handler, but the error text is Rust's own wording. Cosmetic.
- src/bot.js partials: serenity has none. The gateway builds payloads from raw events and pre-update snapshots. A presence update for a member not in the cache is dropped: serenity only adds the member when the full user is sent, while discord.js adds a role-less partial member and dispatches (liverole). Edge case, user-visible for liverole on uncached members.
- src/bot.js makeCache: GuildStickerManager, GuildScheduledEventManager, StageInstanceManager and ThreadMemberManager have no limit-0 equivalent; serenity keeps stickers, scheduled events and stage instances on the guild. Memory only.
- src/bot.js sweepers: the 3 h message lifetime is emulated (older cached messages count as uncached), but nothing is evicted beyond 200 per channel. discord.js's archived-thread sweeper is not ported, so archived threads stay cached longer than in JS. Edge case.
- src/bot.js reportFatal / 'Discord login failed with <code>': logged only when the login itself fails (gateway lookup 401). A fatal close code during IDENTIFY parks with the default PARKED text. Cosmetic.
- events/threadDelete.js (ThreadDeleteAction emits only for a cached thread): Rust dispatches threadDelete for uncached threads too. feat-logging then logs a bare thread, and modmail closes the conversation, where the JS would do neither. Left in place because feature crates rely on it. User-visible (extra log entries).
- events/channelCreate.js (ChannelCreateAction emits only when the channel was not already cached): Rust dispatches every CHANNEL_CREATE, including channels the bot just created and cached over REST. In the JS this is race-dependent. Edge case, possible extra 'channel created' log.
- events/guildMemberUpdate.js: serenity's cache never updates a member's `flags` or avatar decoration from GUILD_MEMBER_UPDATE. After one change of either, later no-op updates are still dispatched, and hooks see stale flags. The 'collectibles' nameplate fields discord.js compares do not exist in serenity 0.12.5. Edge case.
- events/presenceUpdate.js: serenity removes offline presences from its cache, so an offline→offline update still counts as a change and is dispatched. Edge case.
- events/threadCreate.js newlyCreated: serenity drops the flag. Approximated as 'not cached before and created less than 60 s ago'. Edge case.
- events/guildBanAdd.js and guildBanRemove.js: the reason is always None (discord.js has none from the gateway either). No difference.
- interactionRouter.js / discord.js transformOption: channels picked in a CHANNEL option are not added to the serenity cache. Cache-only readers treat an uncached pick (mostly archived or private threads) as missing; check_channel_usable_fetch / fetch_channel are the workaround. Edge case, user-visible for threads.
- PinMessages permission (bit 51): serenity 0.12.5 has no such flag and truncates it on deserialize, so missing_bot_permissions can never report it (feat-automations pin pre-check). Cannot be fixed without a serenity upgrade. User-visible: a pin refused by Discord is counted as an automation run.
- utils/guildMembers.js fetchAllMembers: Rust pages over REST (GET /guilds/{g}/members, 1000 per page) instead of gateway opcode 8, with a fixed 30 s pause after a 429. Slower on large guilds. Edge case.
- guild_members::fetch_members_by_ids without a gateway sender (only in tests or before login): every failed REST lookup counts as 'not a member'; has_chunk_sender lets callers check. Edge case.
- interactionHelpers.js respondAutocomplete: a choice whose value is null is dropped (the JS sends it and Discord rejects the whole answer). The 100-unit cut never splits a surrogate pair (the JS can). Edge case.
- interactionHelpers.js missingBotPermissions: an unknown permission key is warned about on every call; the JS warns once per key. Cosmetic.
- newTargets.js findByName: an existing role or channel is matched in id order, where discord.js uses cache order. This differs only when two names match case-insensitively. Edge case.
- redis.js pushRecent with a TTL of 0 or none: Rust returns null without pushing. The JS pushes, then EXPIRE 0 deletes the list (or EXPIRE NaN fails after the push). No caller passes such a TTL. Edge case.
- settingsService.js reviveSettings: a cached row with the right marker that Rust cannot decode (for example a column added by a newer JS build) is treated as a miss and its key deleted; the JS would use it. Edge case.
- commandLoader.js loadCommands log lines ('Loaded N command(s).', order around plugin install) are not byte-identical to the JS. Cosmetic.
- bot-core testing: set_discord is a OnceLock, so a second set_discord in a test is ignored (audit-1 request still open). Tests only.
- bot-core collectors: no message collector and no messageDelete/channelDelete/guildDelete collector end reasons (wave-b feat-games request). feat-games keeps its own boot hook and driver. No user-visible difference today.
