# dash-schema: public API (from its author)

I ported both JS files in full and wrote no stubs.
- src/dashboard/schema.js -> rust/crates/dash-schema/src/schema.rs. This covers:
  - FIELD_TYPES, CHANNEL_KINDS and channelKind.
  - The Field descriptor type, kept as an ordered JSON map so key order is preserved.
  - validateValue for all 22 types, readValue, checkRefs, collectStoredRefs, collectAssignableRoles, refKey, storedRefKeys, publicDescriptor and lintDescriptors.
- src/dashboard/fields.js -> rust/crates/dash-schema/src/fields.rs plus src/fields_data.json.
  - The JSON holds every group and descriptor exactly as publicDescriptor serves them: 202 fields, including the 42 module flags.
  - It also holds the restated constants, SETTINGS_COLUMNS, JSON_COLUMNS, NOT_EXPOSED and the JS hook table.
  - It is generated by rust/fixtures/gen/dash-schema-golden.mjs and embedded with include_str!.
- All 48 server-only hooks (read/check/normalize/write) are restated in Rust: messageField, automod rules and lists, honeypot, escalation, logEvents, welcome embeds and card style, the captcha panel and button, xpBoostRoles, timezoneRoles, rankCardStyle, currency, achievementMessage, autoThreadChannels and voiceRoleLinks. A test checks that the Rust hook set equals the JS one field by field.
- Also ported: normalizeEscalation, automodConfigOf, normalizeAutomodWord/Domain, canonicalZone, embedHasContent, readSettingsValues, collectSettingsRefs/RefKeys, validateSettingsChanges, toStoredChanges and checkCrossFields.
- src/js.rs holds the JS value semantics the port needs:
  - integral floats are written as integers;
  - String(x) and Number(x);
  - strict equality;
  - Object.keys order, where integer-like keys come first;
  - Math.round.

Tests: tests/golden.rs and tests/registry.rs, 27 tests.
- The goldens come from the JS: every settings field and every nested or synthetic descriptor, each run against about 200 probe values (validate, normalise, refs, toStoredChanges with and without a stored row, readValue, stored refs and ref keys).
- They also cover 8 sample rows, the helpers, checkRefs, collectAssignableRoles, lint and PATCH bodies. That is about 290k comparisons.
- The general and module groups and the subToggle data are byte-identical to fixtures/golden/dashboard-catalog.json.
- The settings-registry cases from test/dashboard.test.js are ported, checked against prisma-dmmf.json, LIMITS and MODULES.
- A database test reads the two GuildSettings rows the JS toolchain seeded in mock DB dash_schema through bot-db. It compares readSettingsValues, the refs and a full re-save with what the JS answers for the rows Prisma reads back.
- test/sec-dashboard*.test.js and review-dashboard*.test.js contain no schema or fields cases; they test HTTP, auth and collections.

## API

All items are re-exported at the dash_schema root. A GuildSettings row is passed as JSON: what Prisma returns, built with `row_json(&bot_db::models::GuildSettings)`. `Option<&Value>` where `None` means JS undefined.

Look up a field:
- `settings_field(name) -> Option<&'static Field>`
- `registry()`: `.settings_fields`, `.module_groups`, `.general_groups`, `.settings_columns`, `.json_columns`, `.not_exposed`, `.constants`
- `module_groups(key)`, `general_groups()`, `settings_column(field)`, `is_json_column(col)`, `constants()` (DEFAULT_TEXTS, DEFAULT_EMBEDS, NUMBER_LIMITS, AUTOMOD_*, LOG_EVENTS, TIER_ACTIONS, ...), `max_settings_changes()`
- `Field` accessors: `field()`, `ty()`, `label()`, `description()`, `default_value()` / `default_or_null()`, `nullable()`, `required()`, `assignable()`, `number(k)`, `string(k)`, `get(k)`, `channel_types()`, `option_values()`, `children()`, `child(name)`, `with(k, v)`, `raw()`

JSON for the front end:
- `public_descriptor(&field)` / `field.public_json()`: the raw map minus server-only keys, in the descriptor's own key order.
- `Group::public_json()` is catalog.js `publicGroup`: `{id, title, description?, fields}`.
- Catalog subToggles are `{field, label, description, default}` of `settings_field(...)`.
- Output is byte-identical to dashboard-catalog.json.

Validate and normalise one value:
- `validate_value(&field, &value, path: Option<&str>, &mut Refs) -> Result<Value, FieldError{path, message}>`
- `read_value(&field, raw: Option<&Value>) -> Value` (lenient, never fails)
- `validate_setting(name, &value, &mut Refs)` runs validate_value, then the field's check and normalize hooks.

GET settings:
- `read_settings_values(Some(&row)) -> Map`, in SETTINGS_FIELDS order.
- Like JS settingsBridge.readGuildSettings, upgrade a v1 automodConfig with the automod service's normalizeConfig first. `automod_config_of` reads v2 only.

PATCH settings, in this order:
1. `validate_settings_changes(&body) -> Result<ValidatedChanges{changes, refs}, SettingsError{message, path}>`
2. `check_refs(&refs, &GuildResources{channels: id->ChannelInfo{kind: channel_kind(type)}, roles: id->RoleInfo{everyone, managed, assignable}}, &collect_settings_refs(row).to_keep())`. Use `collect_settings_ref_keys(row)` and `ref_key(path, id)` for the per-field role-keep rule of server.js.
3. `to_stored_changes(&changes, row) -> Map` (columns to write)
4. Merge the result into the row.
5. `check_cross_fields(Some(&merged), Some(&changes)) -> Option<CrossProblem{path, message}>`
6. Write, storing null in an `is_json_column` column as SQL NULL.

Collections (dash-collections):
- Build descriptors with `Field::from_json(json!({...}))`, written in JS key order.
- Then use `validate_value`, `read_value`, `default_or_null`, `collect_stored_refs(&f, raw, &mut StoredRefs)`, `stored_ref_keys(&f, raw, path, &mut IndexSet)`, `collect_assignable_roles(&fields, record)` and `lint_descriptors(&fields, prefix)`.
- Use `js::js_keys(map)` for the unknown-key loop of validateRecordInput, so the first error path matches the JS.

Helpers:
- `normalize_escalation`, `automod_config_of`, `normalize_automod_word` / `_domain` (plus `_str` variants), `embed_has_content`, `canonical_zone`, `is_snowflake`, `channel_kind`
- `hook_read` / `hook_check` / `hook_normalize` / `hook_write` for the per-field hooks
- `js::{js_num, canon, round2, to_number, strict_eq}`

## Known gaps

- schema.js validateValue/readValue, type 'datetime': V8's legacy Date.parse fallback accepts non-ISO strings and numbers ("12345", "#000000", 0, "March 1 2026") as local-time dates. bot_util::js::date_parse reads only ISO-8601 and HTTP dates, so Rust refuses them, or reads them as the default. The front end and the bot only send ISO strings. In the golden test exactly these cases are skipped (known_gap).
- fields.js normalizeEscalation: a stored countFrom in a non-ISO format that only V8's legacy parser understands becomes null in Rust; the JS keeps it. Same cause as the datetime gap.
- schema.js validateValue, type 'emoji' (also the currencyEmoji setting): the JS regex is /\p{RGI_Emoji}/v. Rust uses bot_core::custom_embed::is_unicode_emoji, which accepts any ZWJ chain of emoji, so a non-RGI sequence such as 🐶‍🐱 is accepted in Rust and refused in JS. RGI ZWJ sequences and everything else agree. These probes are skipped in the golden test.
- schema.js validateValue 'text'/'stringList': a descriptor whose `pattern`/`itemPattern` is not valid regex makes the JS throw a SyntaxError (a 500 from the server). Rust answers the FieldError 'has an invalid format.' No shipped descriptor has such a pattern.
