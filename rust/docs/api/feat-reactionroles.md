# feat-reactionroles: public API (from its author)

I ported all five JS files to rust/crates/feat-reactionroles (register(reg) is the only entry point; every module is pub).
- src/services/reactionRoleService.js -> src/reaction_role_service/, split into:
  - pure.rs: constants, emoji and link parsing, names, error texts, payload builders, the planner
  - emoji_tables.rs: V8's Unicode 17 emoji property tables, generated by fixtures/gen/feat-reactionroles-emoji-tables.mjs
  - store.rs: every Prisma query, plus RAW_SQL
  - index.rs: the panel index (memo, generations, shared in-flight load, Redis key guild:{g}:rrpanels with TTL 300)
  - discord.rs: the RrDiscord trait over every discord.js call, with SerenityRr as the production implementation; tests install a fake with set_discord_ops
  - engine.rs: sync and fetch, reactions, role checks and changes, prune, runPlan, rate limit, suppression, background tasks
  - handlers.rs: the rr and rr-select handlers and all hook bodies
- src/services/roleTemplateSetup.js -> src/role_template_setup.rs. It includes upgradeTimezonePanels with a PanelStore trait so tests can use a fake store.
- src/utils/roleTemplates.js -> src/role_templates.rs.
- src/plugins/reaction-roles.js -> src/plugin.rs: 7 hooks, the 2 components, the guildReady upgrade with a 60 s timeout.
- src/commands/admin/reactionrole.js -> src/commands/reactionrole.rs: all 8 subcommands, both autocompletes and buildListPages, with the JS texts. customIds are byte-identical (rr:{groupId}:{roleId}, rr-select:{groupId}), and old cuid group ids still route.

Tests: 2 binaries plus a shared fake (tests/common).
- offline.rs:
  - golden checks of the command and plugin
  - JS-generated fixtures (fixtures/gen/feat-reactionroles-golden.mjs -> fixtures/golden/feat-reactionroles/golden.json) for: an 8080-entry emoji sweep against V8, parseEmojiInput, message links, names, the planner over every input combination (more than 1000 cases), 25 panel payloads, select rows, footers, customIds, the index key, list pages and templates
  - ported JS tests 1-20 and all of role-templates.test.js
  - SerenityRr checked against a FakeGuild
- db.rs:
  - JS cases D1-D23 through the router with the mock DB
  - cross-language tests in both directions (fixtures/gen/feat-reactionroles-js.mjs): rows, the Redis index read by the other side, searchPanels/searchItems/listPanels compared with Prisma's results, and the rate-limit window (JS makes 8 hits, then Rust's ninth check is over the limit)

## API

Use feat_reactionroles::reaction_role_service as rr (everything is re-exported there) and feat_reactionroles::role_template_setup.

DB functions (take &PgPool and plain ids; Panel = { group: bot_db::ReactionRoleGroup, items: Vec<ReactionRoleItem> }; PanelDraft is the JS draft shape):
- get_panel(pool, guild, id) -> Option<Panel>
- count_panels
- find_panel_by_message -> Option<PanelRef{id,title}>
- search_panels(pool, guild, q) and search_items(pool, guild, panel, q, &role_ids), with the JS row shapes
- list_panels -> Vec<PanelListRow>
- create_panel(pool, &PanelDraft); draft_item(group_id, &NewItem, position)
- add_item(pool, group_id, &current_items, &NewItem): a duplicate role fails with a DbError where is_unique_violation() is true (Prisma's P2002)
- insert_items(pool, group_id, &existing, &[NewItem], &order); order_items
- remove_item(pool, group_id, item_id)
- update_panel(pool, guild, id, &PanelPatch) -> Option<Panel>
- delete_panel, move_panel(pool, guild, id, channel, message, attached)
- list_unique_panels

Index (take &App): get_panel_index, peek_panel_index, invalidate_panel_index (call after every mutation), set_panel_index, reset_panel_index.

Discord-side functions (take &App and plain ids):
- mark_panel_missing(app, guild, panel_id)
- fetch_panel / fetch_panel_message -> Fetched::{Ok{channel,message}, Missing, Failed}
- sync_panel(app, guild, PanelArg::Id(id) or PanelArg::Row(Box<Panel>), color) -> SyncResult{status,code,reason}
- add_panel_reaction, ensure_panel_reactions(app, &MessageInfo, &index_items(&panel.items)), remove_panel_reaction, remove_own_reactions
- prune_items_for_role(app, guild, role) -> usize
- run_plan / execute_plan
- idle(app) waits for background work

Pure functions: build_panel_payload(&PanelView, color) -> PanelPayload, with .to_json() for the JS shape and .to_api_body() for the REST body; Panel::view() and PanelDraft::view() produce the PanelView. Also build_select_row, panel_footer, plan_role_change, parse_emoji_input(input, &GuildEmojis{ops,guild_id}), parse_message_reference, describe_discord_error(code), emoji_key_of_stored, is_unicode_emoji, component_emoji, index_key, rate_key.

Constants:
- Iterable tables: RR_TYPES, RR_LAYOUTS, MAX_ITEMS, STYLE_MAP, TYPE_LABELS, LAYOUT_LABELS, DEFAULT_DESCRIPTIONS, PLACEHOLDERS, RR_TEMPLATE_KEYS, DEFAULT_TITLE
- Lookups: max_items, style_map, type_label, layout_label, rr_template(key)

Discord access: discord_ops(&app) returns Arc<dyn RrDiscord>; set_discord_ops installs a fake in tests.

Role templates:
- role_template_setup::setup_role_template(app, guild, key, executor: Option<&Member>, reason) -> anyhow::Result<SetupResult{roles,created,reused}>; downcast the error to RoleTemplateError for the admin-facing message
- describe_setup(created, reused), describe_reused(&roles)
- upgrade_timezone_panels(app, guild)
- role_templates::{role_templates(), get_role_template(key), role_template_keys()}

Command: commands::reactionrole::{build_list_pages, template_choices}.

## Known gaps

- reactionRoleService.js buildPanelPayload: a panel with an empty description (description '') and no listing (BUTTONS/SELECT with items) makes discord.js's EmbedBuilder.setDescription throw. Rust sends an empty description instead, which Discord rejects with 50035. syncPanel ends 'failed' either way, but /reactionrole create answers 'Could Not Post' where the JS answered 'Something Went Wrong'. I removed this case from the golden fixture because the JS cannot produce it.
- reactionRoleService.js verifyRoles/roleVerdict: in JS the forced roles.fetch puts a role that exists but was not cached into the cache, and the change goes ahead. Rust's REST check (RrDiscord::fetch_role_exists) does not fill serenity's cache, so such a role is reported 'I couldn't check that role right now' until the gateway caches it. Deleted roles are still confirmed and pruned the same way.
- reactionRoleService.js handleRoleButton/handleRoleSelect: the JS answers OOPS when interaction.guild is not cached. Rust needs only the guild id and the member, and goes on.
- reactionRoleService.js fetchPanelMessage: a channel id that belongs to another guild gives a non-numeric GuildChannelUnowned error in JS, so the result is 'failed'. In Rust SerenityRr::fetch_channel returns code 10003, so the result is 'missing' and the panel is flagged.
- reactionRoleService.js hasManageMessages(guild, channelId, fallbackChannel): the fallback (the reacted message's channel object) is not used. Only the cached panel channel is checked, so an uncached channel counts as 'no Manage Messages'.
- reactionRoleService.js fetchPanelMessage (channel.messages.fetch): SerenityRr::fetch_message always goes to REST first, because serenity's message cache does not track reaction events while discord.js's does. The cached copy is used only when there is no REST client (offline).
- roleTemplateSetup.js setupRoleTemplate/upgradePanel: the role is created with an explicit REST body {name, permissions:'0', mentionable:false, hoist:false, colors:{primary_color}} (only when the color is not 0). discord.js builds its own body from colors.primaryColor, so the exact JSON may differ (for example secondary/tertiary null). A failed timezoneRoles save comes back as a plain error, not a RoleTemplateError, which matches the JS rethrow.
- reactionrole.js with new_role:/new_channel: discord.js caches a created role or channel immediately, and serenity does so only on the gateway event. The command works around this inside the crate: the role is taken from the interaction's resolved data and added to a clone of the cached guild for checkAssignableRole, and an uncached channel is fetched over REST and checked with channel_usable_verdict. This matches the JS when the gateway is slow, but each such channel check costs a REST call.
- Regex and grapheme data: UNICODE_EMOJI_RE uses property tables copied from V8 (Unicode 17, ICU 78.3). Graphemes come from unicode-segmentation, not Intl.Segmenter. The 8080-entry sweep matches V8 exactly, but a future Node or ICU upgrade would need the tables regenerated with fixtures/gen/feat-reactionroles-emoji-tables.mjs.
