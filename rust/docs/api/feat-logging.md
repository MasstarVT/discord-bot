# feat-logging: public API (from its author)

The crate was empty after the crash, so all seven JS files were ported from scratch and are now complete. Build, tests and clippy all pass.

- src/services/loggingService.js -> src/logging_service.rs: LOG_TYPES as the `LogType` enum, LOG_EVENTS (32 entries), the settings predicates, toggleLogEvents, channelCleanupData, channelTypeLabel, extractMentions, fitEmbedData / embedLength, the dead-channel memo, the per-channel queue (10 embeds / 6000 chars per post, 100-item cap with a 'dropped' notice, 1 s flush), getLogChannelHealth, sendLog, and flushLogQueue with its shutdown flush.
- src/services/logEvents.js -> src/log_events.rs: every builder and diff, written over plain view structs. src/adapters.rs is new: it fills those views from serenity objects, using discord.js's CDN URL rules.
- src/services/inviteTracker.js -> src/invite_tracker.rs: the snapshot model and its pure functions, plus refreshSnapshot, recordInviteCreate/Delete, trackJoin, trackLeave, getCodeState, deleteDiscordInvite, the stats and leaderboard SQL (RAW_SQL), getJoinRecord, getPersonalInvite and savePersonalInvite.
- src/plugins/logging.js -> src/plugins/logging.rs: all 26 hooks, including the audit-log budget, the bot-managed channel memo, the timeout dedupe key and the channelDelete settings cleanup.
- src/plugins/invites.js -> src/plugins/invites.rs: 5 hooks. The join hook queues `track_join` synchronously, so joins and leaves keep gateway order.
- src/commands/admin/logging.js -> src/commands/logging.rs: every subcommand, plus autocomplete.
- src/commands/utility/invites.js -> src/commands/invites.rs: show, inviter, leaderboard (paginated) and link.

Tests are in tests/logging.rs (41) and tests/invites.rs (26):
- Golden checks: commands, both plugins, 91 builder/diff cases and 19 snapshot cases, the CDN URLs, and the three cache keys. All are compared against output generated by rust/fixtures/gen/feat-logging-golden.mjs into rust/fixtures/golden/feat-logging/cases.json.
- Behaviour: the ported JS tests, plus the send_log queue tests run through a recording `LogApi`.
- Hooks: run through the hook runner against FakeGuild.
- Database: /logging and /invites end to end, attribution end to end, the raid cap, and gateway order.
- Cross-language, both directions, via rust/fixtures/gen/feat-logging-js.mjs: the snapshot in Redis, the GuildMemberCache rows and the personal links; also the timeout dedupe key, using the JS `setNX`.

## API

Entry point: `feat_logging::register(&mut Registry)` registers both commands and both plugins.

**Logging** (`feat_logging::logging_service`):
- `send_log(&App, GuildId, LogType, embed: serde_json::Value, SendLogOpts).await` posts a log embed. It never fails and returns once the embed is queued.
  - The embed is APIEmbed JSON: use `serde_json::to_value(CreateEmbed)` or a builder from `log_events`.
  - Build the options with `SendLogOpts::default().event("key").settings(Some(s)).file(LogFile)`. `SendLogOpts` replaces the JS `normalizeLogOpts`; the legacy Client argument does not exist in Rust.
  - `send_log_by_key(app, g, "MOD", ..)` takes the type as a string and warns once on an unknown key.
- `LogType`: `ALL`, `key()`, `field()`, `label()`, `from_key()`, `channel_of(&GuildSettings)`.
- The event registry: `LOG_EVENTS`, `log_event(key)`, `log_event_keys()`, `MESSAGE_LOG_EVENTS`.
- Predicates: `is_log_event_key`, `is_log_event_enabled(Option<&GuildSettings>, key)`, `toggle_log_events(&[S], name, on)`, `is_ignored_channel(settings, Option<&ChannelChain>)` (build a chain with `ChannelChain::of(app, g, c)`), `channel_cleanup_data(settings, id) -> Option<Map>`.
- Helpers: `channel_type_label(u8)`, `extract_mentions`, `fit_embed_data`, `embed_length`, `to_create_embed`.
- Dead-channel memo: `is_log_channel_dead`, `forget_dead_channels(app, guild, Option<channel>)`, `mark_log_channel_deleted`.
- Channel checks: `get_log_channel_health(app, g, Option<&str>) -> Health { state, missing, text }`, `usable(app, g, Option<&GuildChannel>, needs)`.
- Queue: `flush_log_queue(app, Option<&str>)` and `reset_logging_state`. The bins do not need to call `flush_log_queue`: the shutdown flush is registered automatically on the first `send_log`.
- `set_log_api(app, Arc<dyn LogApi>)` is a test seam for the channel fetch, send and ban audit lookup; serenity is the default.

**Embed builders** (`feat_logging::log_events`, pure, return `Value`):
- `log_embed`, `fit_embed`, and every `build_*_embed` / `diff_*` function, plus `classify_voice`, `is_ghost_ping`, `find_invite_codes`, `build_bulk_delete_transcript`, `format_time_in_server`, `format_bytes`, `user_tag`, `user_line`, `channel_ref`.
- They read plain views: `LogUser`, `LogMessage`, `LogMember`, `LogChannel`, `LogThread`, `LogRole`, `LogGuild`, `LogEmoji`, `LogInvite`, `LogVoiceState`. `feat_logging::adapters::log_*` builds these from serenity objects.

**Message snapshots** (`feat_logging::message_snapshot`, JS `messageSnapshot.js`):
- Same key, JSON shape and TTL as the JS: `msgsnap:<channelId>:<messageId>`, `MESSAGE_SNAPSHOT_TTL_DAYS` (default 7, 1-30). Public: `snapshot_key`, `snapshot_ttl_seconds`, `should_snapshot`, `build_snapshot`, `snapshot_to_message`, `store_snapshot`, `load_snapshot`, `load_snapshots` (one `Cache::mget`), `forget_snapshots`. Delete, edit and bulk-delete logs read it for messages serenity no longer has cached; voice logs also name the channel, since a temporary voice channel may be gone.

**Invite tracker** (`feat_logging::invite_tracker`):
- `refresh_snapshot(&App, GuildId)` returns a `'static` future of `Refresh { ok, reason }`. feat-general can spawn it for `/module enable invites`.
- Snapshot edits: `record_invite_create(app, g, InviteState)` and `record_invite_delete(app, g, code)`.
- Joins and leaves:
  - `track_join(app, g, UserId, joined_ms: Option<i64>, Option<IsEnabled>)` returns a `'static` future of `Option<InviteInfo>`.
  - `track_leave(app, g, UserId)` returns a `'static` future; awaiting it is optional.
  - Both queue on the guild mutex when called.
- `get_code_state(app, g, code, allow_fetch, since_ms) -> CodeLife` and `delete_discord_invite`.
- Database reads and writes:
  - `get_invite_stats(&PgPool, g, user) -> InviteStats`
  - `get_invite_leaderboard(&PgPool, g, limit, &[exclude]) -> Vec<LeaderboardRow>`
  - `get_join_record`, `get_personal_invite`, `save_personal_invite(&App, g, user, code, channel)`
- Pure functions: `is_snapshot`, `parse_snapshot`, `is_trusted_snapshot`, `empty_snapshot`, `build_snapshot`, `apply_invite_create`, `apply_invite_delete`, `resolve_join`, `classify_join`, `compute_stats`, `invite_to_state` / `invite_event_to_state` / `invite_json_to_state`.
- Also public: `snapshot_key`, `raw_sql`, `bot_can_track`.
- `set_invite_api` and `set_trusted_since` are test seams.

**Hook state keys for later `guildMemberAdd` hooks:**
- `"invite"` holds `Option<feat_logging::InviteInfo>` (`{ code, inviter_id, vanity }`). `None` is the JS `null` (unknown); an absent key is the JS `undefined`.
- `"invitePromise"` holds `feat_logging::InvitePending(Shared<BoxFuture<Option<InviteInfo>>>)`. It settles within 7 s and never fails.

**Other public helpers:**
- `plugins::logging::timeout_key(g, member, until_sec)`
- `plugins::logging::has_invite_hint`
- `plugins::logging::is_bot_managed_channel`
- `commands::invites::link_cooldown_key`
- `commands::logging::autocomplete_choices`
- `commands::logging::status_fields`

## Known gaps

- invite_tracker.rs `trusted_since` (inviteTracker.js `trustedSince(guild)` = `client.readyTimestamp`): bot-core has no ready timestamp. The tracker sets 'trusted since' to the app clock the first time the tracker runs in this process (normally the guildReady refresh); `set_trusted_since` sets it explicitly. A snapshot this process takes between install and READY counts as trusted, where the JS would not trust it.
- logging_service.rs `ensure_shutdown_flush` (bot.js shutdown calls flushLogQueue): the shutdown flush (order 20, 4000 ms) is registered lazily on the first `send_log`. plugins.json says `hasInit: false`, so it cannot be registered from a plugin init. If nothing was ever queued, no flush is registered, which is harmless.
- invite_tracker.rs `observe` (inviteTracker.js `observe` with `withTimeout`): on a 5 s timeout, tokio cancels the REST call. In the JS the fetch keeps running in the background.
- log_events.rs `diff_member_update` via adapters.rs `log_member` (logEvents.js `diffMemberUpdate`): added and removed roles are listed in serenity's `member.roles` order (API order), not discord.js's guild role-cache order.
- commands/invites.rs `create_link` (invites.js `createLink`): `deleteDiscordInvite` for a replaced link is awaited before the reply. The JS fires and forgets it.
- plugins/logging.rs `is_bot_managed_channel` (logging.js `isBotManagedChannel`): one `SELECT EXISTS(StatChannel) OR EXISTS(TempVoiceChannel)` replaces the two Prisma `findUnique` calls. The result and the 10-minute memo are the same.
- adapters.rs `log_message` (logEvents.js `extractMentions` reads `message.mentions.roles`): role mentions are named from the guild cache, and roles that are not cached are skipped, as discord.js's resolved collection does.
- plugins/logging.rs `on_channel_update` / `on_role_update` / `on_guild_update` / `on_thread_update` (logging.js): when the gateway payload has no old object (it was not cached), nothing is diffed or logged. discord.js does not emit these events without the old object either. thread update uses an empty old thread, which gives no lines.
- adapters.rs `log_guild` / `log_partial_guild` (logEvents.js `diffGuild` 'AFK Timeout'): serenity stores `afk_timeout` inside `afk_metadata`, which is `None` when no AFK channel is set. Both sides then default to 300, so an AFK-timeout change on a guild without an AFK channel is not logged. The JS logs it.
- plugins/logging.rs `on_member_leave` (logging.js `onMemberLeave`): when the member was not cached, the leave is logged from a partial view built from the user (no roles, 'Time in Server: Unknown'), matching discord.js's partial GuildMember.
- invite_tracker.rs `SerenityInviteApi::fetch_vanity`: serenity's `get_guild_vanity_url` drops `uses`, so the crate sends its own `GET /guilds/{id}/vanity-url` request through `Http::fire` to read `{ code, uses }`.
- invite_tracker.rs `invite_to_state` (inviteToState): serenity's `RichInvite` has no `expires_at`. The expiry is computed as `created_at + max_age`, which is discord.js's fallback for `expiresTimestamp`.
- commands/logging.rs `sub_ignore_add`: the category name and type come from the resolved option when present, otherwise from the cached channel.
