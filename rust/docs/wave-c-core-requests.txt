[bot] bot-core client::Bot: `wait(self)` consumes the Bot, so `shutdown(&self)` and `all_shards_ready(&self)` cannot be called while the client task is awaited. bins/bot keeps a BotHandle (app, shard_manager, gateway, shards) and re-implements both from public parts. Please add `Bot::wait(&self)` or a `split()` that returns a handle plus the join future.

[bot] bot-core registry::Registry: there is no way to take the plugins or commands by value (the test rebuilds each Plugin from its public fields to call collect_plugins) and no way to reorder commands. Please add `Registry::into_parts()` and a `sort_commands_by(..)`, so the binary can load commands in the JS walkDir order.

[bot] feat-levels xp_service: it keeps its own ready time (`set_ready_at` / `ready_at`) instead of reading `App::ready_at_ms()`. bins/bot copies the value over once the first shard is ready (`bot::bot::sync_levels_ready_at`). feat-levels should read `app.ready_at_ms()` directly.

[bot] bot-db migrate::plan: an applied migration whose checksum no longer matches stops the run with an error, where `prisma migrate deploy` only warns. Since the binary migrates on every start, that mismatch makes it exit 1 on every start. Please make it a warning, or give the bot a non-fatal mode.

[bot] bot-config HOOK_ORDER: list `games-fixes:numguess` under messageCreate, or add the message collector feat-games asked for in wave-b-core-requests.txt. The binary's test allows it as the only boot-registered hook outside HOOK_ORDER.

[bot] bot-core command::DeployConfig::from_env: the default hash file is './.deploy-hash' relative to the working directory, not the repository root as in the JS. bins/bot builds its own DeployConfig from its root path.

[bot] bot-core cache::RedisBackend::is_ready is private; a public `is_ready()` would let the start-up test assert that Redis closed at shutdown.
