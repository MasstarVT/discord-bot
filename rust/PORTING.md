# Rust port: the contract

The JavaScript bot in this repository (`index.js`, `dashboard.js`, `src/`, `prisma/`, `test/`) is being ported to Rust in `rust/`.
The JS code is the specification. Read `CLAUDE.md`, `docs/claude/architecture.md` and `docs/claude/modules.md` for how it works.
The Rust bot must be a drop-in replacement: same commands, same behaviour, same text, same database, same cache, same `.env`.

## Hard rules for everyone working on the port

1. Write only inside `rust/`. Everything else in the repository is read-only reference. Never commit, push, or change branches.
2. Write only inside the crate(s) you were given. Do not edit another crate, the workspace `Cargo.toml`, or `PORTING.md`
   (foundation agents may add lines to `[workspace.dependencies]`; nobody reformats that file). If something in a crate you
   do not own is missing or wrong, work around it inside your own crate and list it under `core_requests` in your report.
3. No stubs. No `todo!()`, `unimplemented!()`, empty handlers, "left as an exercise" or silently dropped subcommands, options,
   buttons, hooks or jobs. If a behaviour cannot be reproduced (for example it leans on a discord.js internal), build the
   closest working behaviour and list it under `gaps` in your report, with the JS file and function.
4. User-visible text (embed titles, descriptions, error messages, button labels, emoji, placeholders, command and option
   names and descriptions) is copied verbatim from the JS.
5. Never guess a library API. The sources of every dependency are on disk under `~/.cargo/registry/src/` once fetched;
   read them (or docs.rs) for exact signatures. Versions are pinned in the workspace `Cargo.toml`.
6. No git attribution lines, no model names, no real names or email addresses in any file. Author is `MasstarVT`.

## Data compatibility (the reason the tests exist)

The Rust bot starts against the database and cache the JS bot has been using, with no migration step and no data loss.
Switching back to the JS bot must also keep working, so both sides read what the other wrote.

- **PostgreSQL.** The schema is `prisma/schema.prisma` and `prisma/migrations/` exactly as they are: same tables, columns
  (Prisma's quoted camelCase names), enum types, indexes. Never add, rename or drop anything. Things Prisma did in the
  client that Rust now has to do by hand: `@updatedAt` columns are set in every `UPDATE` and `INSERT`; `@default(cuid())`
  and `@default(uuid())` ids are generated in Rust (`bot_db::new_cuid()`); `DateTime` is `timestamp(3)` in UTC without a
  zone; `Int` is `i32` (clamp, never overflow); `BigInt` is `i64`; `Json` is `serde_json::Value`; `String[]` is `Vec<String>`.
  Raw SQL in the JS (`$queryRaw`, `$executeRaw`, advisory locks, `FOR UPDATE SKIP LOCKED`) is ported statement for statement.
  `rust/fixtures/golden/prisma-dmmf.json` is Prisma's own description of the data model.
- **Redis.** Key names are byte-identical to the JS (see the key table in `docs/claude/architecture.md`). Values are what
  `JSON.stringify` wrote: dates are `2026-01-02T03:04:05.678Z` strings, absent optional fields may be missing or `null`,
  numbers may be integers or floats, and a value that is not JSON is the raw string. TTLs are the same. A value Rust cannot
  read is treated as a cache miss, never as an error and never as a deletion of the underlying data.
- **Scheduled jobs.** `ScheduledJob` rows written by the JS bot (type, `dedupeKey`, payload JSON shape) run under Rust.
- **Component ids.** `customId` strings are identical (`prefix:param1:param2`, registry in `src/config/customIds.js`), so
  buttons, selects and modals on messages the JS bot already posted keep working.
- **Slash commands.** The payload sent to Discord for every command is JSON-equal to
  `rust/fixtures/golden/commands.json` (`payload`), and its routing metadata (`module`, `gated`, `permissionLevel`,
  `subcommandPermissions`, `allowInDMs`, `hasAutocomplete`) matches too.
- **Environment.** Every key in `.env.example` keeps its name, default and meaning. State files (`STATE_DIR`,
  `DEPLOY_HASH_FILE`) keep their formats. The dashboard's sealed session cookie keeps its format.

## Reference data from the JS bot

`rust/fixtures/golden/` is generated by `node rust/fixtures/gen/dump-golden.mjs` (run from the repository root; Node 24 and
`node_modules` are installed; Redis connection errors in its output are expected). Files: `commands.json` (79 commands), `config.json` (everything `src/config/*.js` exports), `plugins.json`
(43 plugins: hooks, components, jobs, providers), `prisma-dmmf.json` (58 models, 28 enums), `dashboard-catalog.json`.
When a test needs more reference data (a Redis value, a rendered embed, a parser result), add a small Node script under
`rust/fixtures/gen/<crate>-*.mjs` that produces it from the JS code and writes `rust/fixtures/golden/<crate>/*.json`.
Generated from the JS is always better than typed by hand; the JS tests in `test/` show how to stub Redis, Prisma and
discord.js objects.

## Workspace layout

`rust/Cargo.toml` is a workspace (`crates/*`, `bins/*`). Crate skeletons already exist; fill in the one you own.

| Crate | Ports | Depends on |
|---|---|---|
| `bot-config` | `src/config/*` | nothing |
| `bot-db` | `src/database/*`, the Prisma data model as Rust types, the migration runner | `bot-config` |
| `bot-util` | the pure parts of `src/utils/*` (no Discord types) | `bot-config` |
| `bot-cards` | `welcomeCard.js`, `profileCard.js` (PNG rendering) | `bot-util` |
| `bot-core` | `src/handlers/*`, `src/services/{redis,settingsService,scheduler,rewards}.js`, the Discord-facing utils, the plugin/command/hook framework | all of the above |
| `feat-*` | one group of modules each: its `src/services`, `src/commands`, `src/plugins` files and tests | `bot-core` (and listed `feat-*` crates) |
| `dash-schema` | `src/dashboard/{schema,fields}.js` | `bot-core` |
| `dash-auth` | `src/dashboard/{config,auth,siteParts,docs,changelog,commandList}.js` | `bot-core` |
| `dash-collections` | `src/dashboard/collections/` (definitions, not `*.store.js`), `catalog.js`, the bridge and store traits | `dash-schema` |
| `dash-records-a`, `dash-records-b` | `src/dashboard/collections/*.store.js` | `dash-collections`, feature crates |
| `dash-server` | `src/dashboard/{server,discordApi,landing}.js`, the static files | the other `dash-*` crates |
| `bins/bot`, `bins/dashboard` | `index.js` + `src/bot.js`, `dashboard.js` (+ `recordsBridge.js`, `settingsBridge.js`, `tasks.js`) | everything |

`rust/docs/groups.json` lists exactly which JS files each `feat-*` crate owns (`node rust/fixtures/gen/group-deps.mjs`
checks it against the JS import graph). Every public function a JS service exports is a public function of the Rust
crate with the same meaning, because later crates and the dashboard call it; describe that API in your report.

Inside a crate, mirror the JS file names in snake_case (`moderationService.js` becomes `moderation_service.rs`,
`commands/moderation/ban.js` becomes `commands/ban.rs`) so a reviewer can put the two side by side.
Once it exists, `rust/docs/FRAMEWORK.md` is the guide for writing a feature crate; follow it exactly.

## Building and testing

- Several agents build at once. Use your own target directory so builds never wait on each other:
  `export CARGO_TARGET_DIR="$(pwd)/target-agents/<your-crate>"` from `rust/` (start by copying the prebuilt cache:
  `mkdir -p target-agents && cp -a target-seed "target-agents/<your-crate>"`; that saves recompiling the dependencies and
  the foundation crates). Build and test only your crate: `cargo check -p <crate>`, `cargo test -p <crate>`,
  `cargo clippy -p <crate> --all-targets`. Never run a workspace-wide cargo command and never use `rust/target/`.
- Tests are offline by default, like `npm test`. A test that needs PostgreSQL reads `TEST_DATABASE_URL` and one that needs
  Redis reads `TEST_REDIS_URL`; without the variable it returns early (printing `skipped: <VAR> not set`). Keep decision
  logic, parsing, formatting, payload building and state machines in pure functions and test those offline; use
  `bot-core`'s in-memory cache for cache behaviour.
- **The mock database is running on this machine; use it.** `rust/mockdb/` holds a real PostgreSQL 17 (127.0.0.1:54329)
  and a Redis-protocol mock (127.0.0.1:63799; it implements the commands the bot uses, it is not Redis). From the
  repository root, `eval "$(node rust/mockdb/mockdb.mjs db <your_crate_with_underscores>)"` gives you a private database
  and a private Redis database number and exports `TEST_DATABASE_URL` and `TEST_REDIS_URL` (run it again for a clean
  copy; add the word `empty` for a database with no tables; `node rust/mockdb/mockdb.mjs start` if the servers are down).
  Your database is a copy of a template the JS toolchain built: `prisma migrate deploy` created the schema and
  `rust/mockdb/seed.mjs` wrote two rows into every table through the Prisma client (guild `900000000000000001` with only
  required fields, guild `900000000000000002` with every column filled; values are synthetic).
  `rust/fixtures/golden/mockdb/baseline.json` is what Prisma reads back for each of those rows. Never touch
  `bot_template`, another crate's database, or Redis database 0. Always run your tests with both variables set before
  reporting; a database test that was skipped counts as not written. Other agents are using the servers at the same
  time: never run `mockdb.mjs stop` or `rebuild`, and give every test its own guild ids so tests in one binary can run
  in parallel.
- **Cross-language tests are the strongest proof of compatibility; every crate with SQL or cache code has them.**
  (1) JS writes, Rust reads: a Node script under `rust/fixtures/gen/<crate>-seed.mjs` sets `DATABASE_URL` and `REDIS_URL`
  from the test variables, then uses the JS bot's own services (not hand-written inserts) to create realistic data: rows,
  cache entries, scheduled jobs. The Rust test runs the script (`node` is on PATH), then reads and uses that data through
  the Rust code. (2) Rust writes, JS reads: the Rust test writes through the Rust code, then runs a Node script that reads
  it back through Prisma or the JS service and prints JSON, which the test compares. `rust/mockdb/selftest.mjs` shows how
  to point the JS code at the test servers.
- What every crate tests: (a) the JS tests for its files in `test/*.test.js`, ported wherever they test logic rather than
  JS plumbing; (b) every Redis key it builds, compared with the key the JS builds, and every cached value shape, read from
  a JS-produced fixture and written back JSON-equal; (c) every scheduled-job payload and `customId` it builds or parses,
  against JS-produced examples; (d) its commands against `commands.json`.
- Done means: `cargo test -p <crate>` passes, `cargo clippy -p <crate>` has no errors, and no rule above is broken.
