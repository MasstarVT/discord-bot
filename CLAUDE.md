# CLAUDE.md

MEE6-style Discord bot, written twice. **Production runs the Rust bot** in `rust/` (serenity 0.12, the bot and dashboard binaries; `rust/README.md`, `rust/PORTING.md`), which the `Dockerfile` builds. The JS bot in `src/` (discord.js v14, ESM, Node 22+) is the reference: the Rust tests compare against JSON generated by running the JS code, and CI still tests the JS. Both share the Prisma 5.22 schema and migrations on PostgreSQL, Redis cache only. Features are modules toggled with `/module` (see `README.md`). Details (grep): `docs/claude/architecture.md` (core, hooks, scheduler, settings, schema, dashboard) and `docs/claude/modules.md` (per module).

## Changing behaviour: JS and Rust
- Every user-visible change lands in both, in this order: the JS in `src/` with its `test/` cases; then `node rust/fixtures/gen/<crate>-golden.mjs` to regenerate `rust/fixtures/golden/<crate>/`; then the matching crate in `rust/crates/` with its tests. A Rust-only change fails the golden tests, and a JS-only change never reaches users. User-visible text in Rust is copied verbatim from the JS.
- Editing `src/dashboard/public/` also needs `node rust/fixtures/gen/dash-server-golden.mjs`, with the file in LF: a CRLF working copy fails the byte-for-byte check on Linux CI.
- Shipping: a push to `main` runs "CI and publish" (JS tests, Rust tests, then the image), and Watchtower restarts the bot about 3 minutes after the image is pushed. Local `npm test` skips the database tests, so wait for that run.

## Commands
JS: `npm run dev|start`, `npm test` (offline; one file: `node --test test/<f>.test.js`), `npm run deploy`, `npx prisma generate` after schema edits, `npm run db:migrate`, `npm run pm2:start|reload|logs`, `npm run dashboard|pm2:dashboard`. Rust: `cargo test -p <crate>` from `rust/`, or `bash rust/run-all-tests.sh` (database tests need `rust/mockdb/`; see the Test section of `rust/README.md`). New `process.env` reads go in `.env.example`.

## Rules that bite
JS paths below; the Rust crates mirror them.
- Features auto-load from `src/commands/<category>/`, `src/events/`, `src/plugins/<id>.js`; never edit the loaders. Events only `runHooks`; logic goes in plugins/services.
- Commands export `module` (a `MODULES` key or `null`). New hook ids, customId prefixes and job types go in `src/config/` (`hookPoints.js`, `customIds.js`, `jobTypes.js`) first. Only automod and custom-commands call `ctx.stop()`.
- `GuildSettings` only via `src/services/settingsService.js`; `ensureGuildSettings` before any per-guild row; arrays/JSON via `updateSettingsWith`.
- Schema changes additive only; never edit an applied migration. Raw SQL: `SQL_NOW`/`sqlUtc`, `::bigint` maths, clamp Int columns with `XP_MAX`/`COIN_MAX`.
- Redis: cache only, always a TTL. No `setInterval` (recurring `ScheduledJob`). `logger`, never `console`. Signal handlers only in `index.js`.
- Ack interactions within 3 s (`ackBudgetMs`, `peekSettings`). Nothing may reject unhandled.
- Automod's Personal Info rule (anti-doxxing) uses `src/utils/personalInfo.js`; its regexes are copied verbatim into `bot_util::personal_info`, and `feat-automod`'s sweep test compares the two.
- Dependencies: Dependabot (`.github/dependabot.yml`) covers npm, cargo (`rust/`), docker and actions, and skips majors, so a security fix that needs a major (or a parent that pins an old range) never gets a PR: bump it by hand, or pin a transitive one under `overrides` in `package.json`. Check with `npm audit` and `cargo audit` (from `rust/`). `rustls` 0.22 comes from serenity 0.12's gateway and waits on a serenity release.
- User URLs via `safeFetch`, user regex via `safeRegex`, admin text via `placeholderParser`/`customEmbed`. Never parse `@everyone`. Caps come from `LIMITS` in `src/config/constants.js`.
- New module: flag + migration, `DEFAULT_MODULE_SETTINGS`, `MODULES` entry, commands, plugin, README rows, a `docs/claude/modules.md` section, a registry row, `.env.example` keys, `src/dashboard/catalog.js` entries (category, description, two-letter code) and `fields.js` groups. `test/integration.test.js` checks they agree.

## Registry
Module keys, `GuildSettings` flags, plugin files, job types and core plugins: the module table under "Modules and `/module`" in `docs/claude/architecture.md` (test-checked; keep it complete).
